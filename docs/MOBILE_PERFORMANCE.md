# تدقيق سرعة فتح الهاتف

> **آخر مراجعة:** 26 أكتوبر 2026
>
> **النطاق:** الصفحة الرئيسية، التخطيط العام، الصور، الحزم، التحميل المؤجل، واختبارات عدم الكسر.

## النتيجة الحالية

تمت إزالة روابط preload اليدوية لصورة الـHero من `app/layout.tsx`. كانت هذه الروابط داخل التخطيط العام، لذلك كانت تُضاف لكل المسارات، بما فيها صفحات الإدارة التي لا تستخدم صورة الـHero. وفي الصفحة الرئيسية كانت تتكرر مع preload الذي يولده `next/image` تلقائيًا من `priority`.

النتيجة بعد التعديل:

- الصفحة الرئيسية: preload واحد تديره صورة الـHero بدل preload مكرر.
- صفحات `/admin` و`/admin/login`: لا توجد إحالة إلى صورة الـHero.
- لم يتغير شكل الصفحة أو مصدر الصورة أو سلوك أزرارها.
- لم يتم تعديل قاعدة البيانات أو API أو المصادقة أو التكاملات.

## ما تم قياسه

| الفحص | النتيجة |
| --- | --- |
| `pnpm build` | نجح وبُنيت الصفحات العامة والدول. |
| `pnpm test:country-routes` | نجح: 40 مسار دولة ومحرك عرض مشترك. |
| `pnpm test:security-boundaries` | نجح. |
| `pnpm test:migration-contract` | نجح. |
| `git diff --check` | نجح. |
| فحص preload قبل/بعد | أزيل التكرار من الصفحة الرئيسية، وأزيلت إحالة Hero من الإدارة. |

هذه قياسات build/static وليست بديلًا عن قياس Lighthouse من جهاز هاتف حقيقي أو بيانات المستخدمين الحقيقية. لذلك لا نضع نسبة تحسن رقمية قبل توفر baseline من URL الإنتاج.

## نقاط قوة موجودة أصلًا

المشروع يطبق بالفعل عدة إجراءات مفيدة للهاتف:

- صورة Hero خاصة بالموبايل `hero-children-mobile.webp`.
- `next/image` مع صيغ AVIF/WebP و`quality={40}` للـHero.
- تحميل GA4 باستخدام `lazyOnload`.
- تحميل فيديوهات الصفحة الرئيسية بعد الاقتراب منها عبر `IntersectionObserver`.
- عدم إنشاء YouTube iframe قبل تفاعل المستخدم في مكونات الفيديو.
- استخدام `content-visibility: auto` لأقسام أسفل الصفحة.
- تقسيم بعض الأقسام والمكونات الثقيلة باستخدام `dynamic`.
- تحميل الخط العربي محليًا مع `display: swap`.

## فرص لاحقة منخفضة المخاطر

قبل تطبيق أي نقطة لاحقة يجب قياسها على Preview ثم على الهاتف:

1. **تسجيل baseline حقيقي:** Lighthouse Mobile وWebPageTest أو Chrome DevTools على الصفحة الرئيسية وصفحة دولة وصفحة `/quran`، مع حفظ LCP وINP وCLS وTotal Blocking Time وحجم JavaScript.
2. **مراجعة شعار الهيدر:** لا نرفع أولوية تحميله إلا إذا أثبت القياس أنه عنصر LCP؛ الأولوية يجب أن تبقى لعنصر Hero فقط.
3. **مراجعة Client Providers:** بعض عناصر الغلاف العامة عميلة بسبب اللغة والمسار. يمكن فصل ما لا يحتاج تفاعلًا إلى Server Components، لكن هذا يحتاج اختبار RTL والتنقل والمصادقة، لذلك لم يُطبق تلقائيًا.
4. **ضغط الصور غير الحرجة:** الصور الحالية WebP وأحجامها معقولة نسبيًا، لكن يمكن إنشاء نسخ أصغر للصور التي تظهر أسفل الصفحة بعد مقارنة الجودة البصرية.
5. **ضبط عتبة الفيديو المؤجل:** يمكن تعديل `rootMargin` بعد قياس وقت ظهور القسم حتى لا يبدأ طلب API مبكرًا جدًا على اتصال بطيء.
6. **إعادة تفعيل حارس أداء في CI:** بعد تثبيت baseline موثوق، يمكن إضافة حدود تمنع زيادة حجم bundle أو تراجع LCP بدل الاعتماد على الانطباع فقط.

## قواعد الأمان أثناء تحسين السرعة

- لا نحذف fallback أو نغير مصدر بيانات دولة من أجل السرعة.
- لا نضع `service_role` أو أسرارًا في العميل.
- لا نعطل RLS أو Route Handlers.
- لا نستبدل preload الأولوي لعنصر LCP قبل قياس البديل.
- كل تغيير أداء يمر عبر build واختبارات المسارات والأمن والعقود، ثم يراجع على Preview قبل الإنتاج.
