# Supabase migration policy

## قاعدة الإنتاج الحالية

المشروع المرتبط بالموقع هو `quran123` (`rjkqyvhbmxrmhsafelao`). يعتمد هذا المشروع على قاعدة معزولة بدأت من baseline باسم `isolated_0001_clean_baseline`، وليس على تشغيل سلسلة الملفات التاريخية `001..051` من الصفر.

## قاعدة التشغيل

لا تُشغّل `supabase db push` على هذه القاعدة اعتمادًا على ترتيب أسماء الملفات التاريخية. ملفات `001..051` محفوظة كسجل تاريخي ومراجعي، وتحتوي على أرقام مكررة وملفات دفع قديمة لا تنتمي إلى baseline الحالي.

أي تغيير جديد يجب أن يكون migration مستقلًا باسم وصفي جديد، ويُطبّق أولًا على بيئة معزولة أو عبر أداة Supabase المعتمدة، ثم يُتحقق من ظهوره في سجل migrations قبل دمج الكود. يجب أن يبقى ملف SQL نفسه في `supabase/migrations/` وبنفس المحتوى الذي طُبق، حتى لا يحدث drift بين القاعدة والمستودع.

## بوابة التحقق قبل الدمج

قبل دمج migration جديدة:

1. راجع الجداول المتأثرة والقيود وسياسات RLS.
2. نفّذ TypeScript وESLint واختبارات حدود الأمان.
3. طبّق migration على بيئة اختبار أو عبر طلب Supabase موثق.
4. تحقق من سجل migrations ومن Supabase advisors.
5. اختبر المسارات العامة والإدارية، ولا تُدخل بيانات اختبار في قاعدة الإنتاج.

المسارات العامة تستخدم `supabaseAdmin` داخل الخادم بعد allowlist؛ لا تستخدم مكونات المتصفح مفتاح الخدمة، ولا تعتمد على anon لقراءة الجداول المحمية. تبقى سياسات RLS العامة محدودة بالصفوف النشطة/المنشورة، بينما الوصول الإداري يمر عبر جلسة الإدارة وواجهات الخادم.
